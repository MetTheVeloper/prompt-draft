## Founder-approved V1 supply schedule

The following issuance schedule is frozen for the first economy simulation:

| Existing score event | Existing XP | Goin V1 | Reference value at 250 toman/goin |
| --- | ---: | ---: | ---: |
| `account_created` | 1000 XP | 10 goin | 2,500 toman |
| `profile_email_added` | 1000 XP | 10 goin | 2,500 toman |
| `referral_joined` | 500 XP | 10 goin | 2,500 toman |
| `referral_reward` | 1000 XP | 20 goin | 5,000 toman |
| `draft_created` | 50 XP | 0 goin | — |

`draft_created` remains XP-only in V1 to avoid turning routine Draft creation into the easiest currency-farming loop.

This policy does **not** define Prompt unlock pricing. Supply policy, sink pricing and the simulation reference value remain independent controls.

## Historical backfill

Migration 023 deterministically backfills already-existing eligible `user_score_events` into `user_economy_events`.

Each issued row records:

```text
event_type = score_reward_issued
source_type = score_event
source_id = <score event id>
source_score_event_id = <score event id>
idempotency_key = score_event:goin:v1:<score event id>
metadata.ruleVersion = 1
metadata.policyKey
metadata.scoreEventType
metadata.scorePoints
metadata.origin = migration_023_backfill
metadata.backfill = true
```

The economy event UUID is deterministically derived from the score-event id for the V1 issuance bridge.

### Critical rerun rule

Historical backfill intentionally uses the frozen V1 literal amounts rather than reading mutable settings.

Reason:

```text
Super Admin changes future issuance
  -> existing historical rewards must not be retroactively repriced
  -> create-schema reruns must remain harmless
```

The per-user economy idempotency key makes the backfill rerunnable without double issuance.

## Future issuance bridge

Migration 023 installs:

```text
user_score_events_goin_issuance
```

an `AFTER INSERT` trigger on `user_score_events`.

For supported score event types the trigger:

1. resolves the current issuance setting;
2. skips issuance when the configured amount is `0`;
3. reads the current issuance rule version;
4. locks the canonical user row;
5. inserts one idempotent `score_reward_issued` economy event.

The trigger approach deliberately reuses the existing reward system regardless of where a score event originates:

```text
account/profile milestones -> backend userScore service
Draft creation              -> backend userScore service
referrals                   -> existing referrals database trigger
```

There is no duplicate referral/account/Draft reward implementation in the economy layer.

## Concurrency contract

Future Goin credits generated by score events lock the same canonical `users` row used by backend debit operations.

This preserves the per-user serialization contract established and locally verified in 21E1.

## Policy version behavior

The current rule version is persisted under:

```text
goin_issuance_rule_version
```

When a Super Admin changes any issuance amount through the economy settings API, the backend increments the rule version atomically.

Future economy events therefore preserve which issuance policy produced them.

Past issued Goin is not rewritten when the policy changes.

## Super-Admin settings contract

Existing route:

```text
GET /api/admin/economy/settings
PUT /api/admin/economy/settings
```

remains protected by:

```text
system.settings.manage
```

Under the current role map this is effectively Super-Admin-only.

The GET response now exposes both the simulation reference value and issuance policy.

Direction:

```json
{
  "unit": {
    "code": "goin",
    "name": "goin",
    "decimals": 0,
    "referenceValueKind": "simulation_reference"
  },
  "goinReferenceValueToman": 250,
  "issuance": {
    "ruleVersion": 1,
    "accountCreated": 10,
    "profileEmailAdded": 10,
    "referralJoined": 10,
    "referralReward": 20,
    "draftCreated": 0
  }
}
```

PUT remains backward compatible with the existing reference-value-only payload and also accepts a partial issuance object:

```json
{
  "issuance": {
    "referralReward": 25
  }
}
```

or both controls together:

```json
{
  "goinReferenceValueToman": 300,
  "issuance": {
    "accountCreated": 12,
    "profileEmailAdded": 12
  }
}
```

Issuance amounts may be integer `0..1,000,000,000` Goin.

A zero value disables future issuance for that reward type without deleting historical rows.

## Audit behavior

Reference value changes continue to create:

```text
economy.goin_reference_value_updated
```

Issuance-policy changes create:

```text
economy.goin_issuance_policy_updated
```

The issuance audit stores:

```text
fromRuleVersion
toRuleVersion
changed fields with before/after values
unit = goin
```

No-op requests create no fake audit event and do not increment rule version.

## Local verification plan

After pulling:

```powershell
git pull
docker compose up -d --build api
docker compose exec api npm run db:schema
```

Expected final migration line:

```text

```

Before evaluating balances, remove synthetic 21E1 verification rows if they still exist:

```sql
DELETE FROM user_economy_events
WHERE idempotency_key LIKE 'verification:21e1:%';
```

Then verify settings:

```sql
SELECT setting_key, integer_value
FROM economy_settings
WHERE setting_key LIKE 'goin_%'
ORDER BY setting_key;
```

Verify deterministic historical issuance:

```sql
SELECT
  score.event_type,
  COUNT(*) AS score_events,
  COUNT(economy.id) AS economy_events,
  COALESCE(SUM(economy.unit_delta), 0) AS goin_issued
FROM user_score_events AS score
LEFT JOIN user_economy_events AS economy
  ON economy.source_score_event_id = score.id
 AND economy.event_type = 'score_reward_issued'
GROUP BY score.event_type
ORDER BY score.event_type;
```

Expected semantics:

```text
account_created/profile_email_added/referral_joined/referral_reward
  -> one economy issuance row per eligible score row

draft_created
  -> zero economy issuance rows in V1
```

Re-running `npm run db:schema` must not increase issued row counts.

A newly created eligible score event must automatically produce exactly one economy event with `metadata.backfill=false`.

## Hard rules

```text
DO NOT convert XP 1:1 into Goin.
DO NOT retroactively reprice historical Goin when settings change.
DO NOT issue Goin for draft_created in V1.
DO NOT duplicate existing reward/business logic in the economy layer.
DO NOT let the frontend choose issuance amounts.
DO NOT let ordinary users/admins mutate economy policy.
DO NOT treat Goin reference value as Prompt unlock price.
DO NOT treat reference value as a fiat redemption promise.
```
